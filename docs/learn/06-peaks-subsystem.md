## 6.1 What is "peaks" data, and why does it exist separately from tags?

If you've ever used a music player — on a phone, in a browser, in a car
stereo — and seen a little horizontal bar that shows bumps and dips as the
song plays (sometimes called a "scrubber" or "seek bar with a waveform"),
that bar is drawing from **peak data**: a pre-computed, compressed summary
of how loud the track is at regular intervals across its length.

A real audio file might contain *millions* of individual sample values
(CD-quality audio samples 44,100 times *per second*). A device like a
Rockbox-powered iPod cannot — and does not need to — read and decode the
entire MP3 just to draw a 300-pixel-wide waveform bar on screen. Instead,
this project pre-computes a **drastically shrunk-down version**: for every
track, it decides on a fixed number of "buckets" (we'll see the exact number
below), and for each bucket it stores a single number from 0–255 representing
"how loud was this segment of the song, roughly." The on-device firmware
then just reads those ~300 bytes and draws ~300 bars — no audio decoding
required on the device at all.

This is a different kind of data from the **tags** you met in Chapter 4.
Tags describe *what* a song is (artist, title, album). Peaks describe
*what the song sounds like over time* — specifically, its loudness contour.
They're generated by a completely different process (decoding audio
samples, not reading metadata frames), they're stored in a completely
different place (separate `.peaks` cache files, not inside the Rockbox tag
cache database), and — importantly — generating them is **much slower**
than reading tags, because it requires decoding the *entire* audio stream
sample-by-sample instead of jumping straight to a small metadata block near
the start or end of the file. That's why this project treats "generate
peaks" as an optional, separately cacheable step (notice the `--peaks` /
`--no-peaks` CLI flags you can see referenced in the tests) rather than
folding it into ordinary tag-reading.

The four files in this package map cleanly onto four questions:

| File | Question it answers |
|---|---|
| `extractor.py` | How do we turn an audio file into loudness numbers? |
| `hasher.py` | What do we *name* the cache file for a given track? |
| `writer.py` | How do we pack those numbers into bytes on disk, and read them back? |
| `manager.py` | How do we do this for an *entire music library*, efficiently, and only when needed? |

We'll walk through them in the order data actually flows: extract → hash
(for naming) → write, then zoom out to see how `manager.py` coordinates all
three for thousands of files at once.

## 6.2 `extractor.py` — turning audio into numbers

### 6.2.1 The shape of the problem

Before we touch any code: an audio *file* (an `.mp3`, `.flac`, etc.) is
**compressed**. The actual numeric samples — plain "how far the speaker
cone should move at this instant" values — are not sitting in the file in
a simple, readable layout. They're encoded with a specific, often
proprietary compression algorithm. To get raw samples back out, you need a
**decoder** for that specific format.

This project doesn't write its own MP3/FLAC/AAC/etc. decoders (that would
be an enormous undertaking — audio codecs are complex). Instead it shells
out to **`ffmpeg`**, a widely-used, free, command-line audio/video
conversion tool, and asks it to decode *any* supported input format into
one simple, universal raw format: **16-bit signed PCM** ("Pulse Code
Modulation" — just a plain sequence of integers, one per audio sample, with
no compression at all).

```python
"""Audio peak extractor streaming raw PCM from ffmpeg."""

from pathlib import Path
import struct
import subprocess

from mutagen._file import File  # pyright: ignore[reportUnknownVariableType]

from dap_db_manager.peaks.writer import PEAKS_NUM_BUCKETS

SAMPLE_RATE: int = 8000  # 8 kHz mono 16-bit signed PCM
BYTES_PER_SAMPLE: int = 2
```

New things here:

- `subprocess` — a Python standard-library module for **running another
  program** (like `ffmpeg`) and capturing its output. This is how Python
  code "talks to" command-line tools that aren't written in Python.
- `mutagen._file.File` — this is the **same third-party tagging library**
  you met in Chapter 4, reused here for a different purpose: not reading
  `artist`/`title`, but reading the track's **duration** (how long the song
  is), which mutagen can usually determine instantly from a file's header
  without decoding any audio. This is much faster than computing duration
  the hard way (counting decoded samples), so it's tried first.
- `SAMPLE_RATE = 8000` — this project deliberately asks `ffmpeg` to decode
  down to a *very* low sample rate: 8,000 samples per second (a real CD is
  44,100/second — more than five times as many). Why? Because we only want
  a rough loudness contour, not audio you could actually listen to. Fewer
  samples to process means extraction is fast, and the final result (buckets
  of 0–255) doesn't need anywhere near CD quality to look right in a tiny
  waveform display.
- `BYTES_PER_SAMPLE = 2` — a 16-bit signed integer takes exactly 2 bytes.
  You saw `struct` format codes like `"<h"` in Chapter 0; `h` is the format
  code for a *signed 16-bit short integer*, and `<` means little-endian
  byte order.

### 6.2.2 `extract_peaks_from_pcm` — the actual math

This is the function that takes raw PCM bytes and produces the final
0–255 peak values. It's pure, dependency-free number crunching — no
`ffmpeg`, no files, just bytes in, a list of integers out. That makes it
easy to unit-test (as `tests/test_peaks_extractor.py` does, feeding it
hand-built byte sequences).

```python
def extract_peaks_from_pcm(
    pcm_bytes: bytes, num_buckets: int = PEAKS_NUM_BUCKETS
) -> list[int]:
    total_samples = len(pcm_bytes) // BYTES_PER_SAMPLE
    if total_samples == 0:
        return [0] * num_buckets
```

- `pcm_bytes: bytes` — a `bytes` object, i.e. an immutable sequence of raw
  byte values (0–255 each). This is Python's basic type for "a chunk of
  binary data," which you saw introduced in Chapter 0.
  `total_samples = len(pcm_bytes) // BYTES_PER_SAMPLE` — since every sample
  is exactly 2 bytes, dividing the byte count by 2 (using `//`, integer
  "floor" division, which drops any remainder) tells you how many actual
  audio samples are in this chunk.
- If there's no audio at all (`total_samples == 0` — e.g. a corrupt or
  silent-length file), it just returns `num_buckets` zeroes rather than
  trying to divide anything by zero further down.

Now the two branches: what happens if the file is *shorter* than the number
of buckets we want versus the normal case (file is much longer than the
number of buckets).

```python
    peaks: list[int] = []

    if total_samples < num_buckets:
        for i in range(num_buckets):
            if i >= total_samples:
                peaks.append(0)
                continue
            chunk = pcm_bytes[i * BYTES_PER_SAMPLE : (i + 1) * BYTES_PER_SAMPLE]
            val = abs(struct.unpack("<h", chunk)[0])
            peaks.append(min(255, int((val * 255) / 32767)))
```

- This is an edge case: a track so short it doesn't even have one sample
  per bucket. In that case, each bucket just gets (at most) one sample's
  value directly, and any buckets beyond the available samples get `0`.
- `struct.unpack("<h", chunk)[0]` — unpacks 2 raw bytes into one signed
  16-bit integer. `struct.unpack` always returns a **tuple** (even for one
  value), so `[0]` pulls out that single number.
- `abs(...)` — loudness here means "how far from silence," which can be a
  negative *or* positive excursion (a speaker cone can push out or pull in);
  we only care about the magnitude, so negative values are flipped positive.
- `32767` is the maximum possible value a signed 16-bit sample can hold
  (`2**15 - 1`). Dividing by it and multiplying by `255` rescales
  "0 to 32767" down to "0 to 255" — squeezing 16 bits of precision into a
  single byte, because that's all the precision a tiny waveform bar needs.
  `min(255, ...)` is a safety clamp in case rounding ever pushes it over.

The normal case — a real song, much longer than 288 buckets — is the
interesting part:

```python
    else:
        for i in range(num_buckets):
            start_sample = (i * total_samples) // num_buckets
            end_sample = ((i + 1) * total_samples) // num_buckets
            if start_sample >= total_samples or start_sample >= end_sample:
                peaks.append(0)
                continue

            chunk = pcm_bytes[
                start_sample * BYTES_PER_SAMPLE : end_sample * BYTES_PER_SAMPLE
            ]
            num_chunk_samples = len(chunk) // BYTES_PER_SAMPLE
            if num_chunk_samples == 0:
                peaks.append(0)
                continue

            chunk_samples: tuple[int, ...] = struct.unpack(
                f"<{num_chunk_samples}h", chunk
            )
            max_val = max(abs(s) for s in chunk_samples)
            # Quantize 0..32767 to 0..255
            norm_peak = min(255, int((max_val * 255) / 32767))
            peaks.append(norm_peak)
```

This is **downsampling**, conceptually: cutting a long sequence of
samples into `num_buckets` equal-sized slices (`start_sample` to
`end_sample` for each `i`), and representing each whole slice by **one
number**. The number chosen here is the slice's *loudest single sample*
(`max(abs(s) for s in chunk_samples)`) — this is a deliberate choice: taking
the maximum, rather than, say, an average, means a single loud drum hit in
an otherwise quiet section still shows up as a visible peak, which is what
you actually want a waveform display to look like (averaging would smooth
everything into a flat, less informative blob).

New syntax you haven't seen in Chapter 0: `f"<{num_chunk_samples}h"` — this
is an f-string *building a `struct` format string*. If `num_chunk_samples`
is, say, `50`, this produces the literal string `"<50h"`, which tells
`struct.unpack` "there are 50 little-endian signed 16-bit integers packed
back-to-back here, unpack all of them at once." That's far faster than
calling `struct.unpack("<h", ...)` in a Python loop 50 separate times —
one call does the whole slice.

Finally, a normalization pass runs over the *whole* list of peaks, after
every bucket has been computed:

```python
    # Dynamic track normalization: scale so track max peak is at least 200/255 if not dead silent
    max_track_peak = max(peaks) if peaks else 0
    if 0 < max_track_peak < 180:
        scale = 200.0 / max_track_peak
        peaks = [min(255, int(p * scale)) for p in peaks]

    return peaks
```

Some tracks are mastered quietly (classical recordings, old masters, etc.)
and would otherwise produce a waveform that barely rises off the baseline —
not very useful visually. This block checks: if the track's single loudest
bucket is below `180` (but not silent, i.e. not `0`), rescale *every*
bucket so the loudest one lands around `200`. That's a `list` comprehension
— `[expression for item in iterable]` — which you met in Chapter 0; here it
builds a brand-new list by scaling each existing peak value.

### 6.2.3 `extract_peaks` — wiring up `ffmpeg` as a subprocess

```python
def extract_peaks(
    audio_path: str | Path, duration_ms: int | None = None
) -> tuple[int, list[int]]:
    path = Path(audio_path)
    if not path.is_file():
        raise FileNotFoundError(f"Audio file not found: {path}")
```

`str | Path` is a **union type hint** (met in Chapter 0): this function
accepts either a plain string path or a `pathlib.Path` object, and
immediately normalizes it to a `Path` either way.

```python
    resolved_duration_ms = (
        duration_ms if duration_ms is not None and duration_ms > 0 else 0
    )
    if resolved_duration_ms == 0:
        try:
            audio: object = File(str(path))
            if audio is not None and getattr(audio, "info", None) is not None:
                info: object = getattr(audio, "info", None)
                length: object = getattr(info, "length", 0.0)
                if isinstance(length, (int, float)) and length > 0:
                    resolved_duration_ms = int(length * 1000)
        except Exception:
            resolved_duration_ms = 0
```

This block tries to get the track's duration *without* fully decoding
audio, by asking mutagen's generic `File(...)` loader to peek at the file's
header (`audio.info.length`, in seconds — hence `* 1000` to convert to
milliseconds). `getattr(obj, "name", default)` is a defensive way to read
an attribute that *might* not exist on every mutagen file type, returning
`default` instead of raising an error if it's missing. If this whole
attempt fails for any reason (`except Exception`), duration just stays `0`
and gets figured out later, the slow way (counting decoded samples).

Now the actual `ffmpeg` invocation:

```python
    cmd = [
        "ffmpeg",
        "-v",
        "error",
        "-i",
        str(path),
        "-f",
        "s16le",
        "-ac",
        "1",
        "-ar",
        str(SAMPLE_RATE),
        "-",
    ]

    with subprocess.Popen(cmd, stdout=subprocess.PIPE, stderr=subprocess.PIPE) as proc:
        try:
            stdout, stderr = proc.communicate(timeout=300)
        except subprocess.TimeoutExpired:
            proc.kill()
            _ = proc.communicate()
            raise RuntimeError(f"ffmpeg timed out decoding {path}")

        if proc.returncode != 0:
            err_msg = stderr.decode("utf-8", errors="ignore") if stderr else ""
            raise RuntimeError(f"ffmpeg failed ({proc.returncode}): {err_msg}")
```

- `cmd` is a **list of strings** — this is how Python's `subprocess` module
  wants a command and its arguments expressed: one list item per
  "argument," instead of one big space-joined string (which avoids a whole
  class of shell-escaping bugs). Translated to a shell command you could
  type yourself, this is: `ffmpeg -v error -i <path> -f s16le -ac 1 -ar 8000 -`.
  Breaking down the flags: `-i <path>` is the input file; `-f s16le` says
  "output format: signed 16-bit little-endian PCM"; `-ac 1` forces mono
  (one audio channel, collapsing stereo down); `-ar 8000` forces our
  8,000 Hz sample rate; the trailing `-` tells `ffmpeg` to write its output
  to **standard output** (a stream) instead of a file on disk.
- `subprocess.Popen(cmd, stdout=subprocess.PIPE, stderr=subprocess.PIPE)` —
  `Popen` launches `ffmpeg` as a separate running process, and
  `stdout=subprocess.PIPE` / `stderr=subprocess.PIPE` tell Python "capture
  what this program prints/outputs, don't let it go straight to the
  terminal — I want to read it myself in Python." `Popen` is itself usable
  as a context manager (the `with` block you met in Chapter 0), which makes
  sure the process's pipes are cleaned up properly even if something goes
  wrong.
- `proc.communicate(timeout=300)` sends no input, waits for the process to
  finish (or up to 300 seconds), and returns `(stdout_bytes, stderr_bytes)`
  — `stdout` here is the **raw decoded PCM audio data** as a plain `bytes`
  object, exactly what `extract_peaks_from_pcm` expects.
  `subprocess.TimeoutExpired` is raised if `ffmpeg` takes too long (e.g. a
  corrupt file that hangs); the code kills the stuck process and raises a
  clearer `RuntimeError` instead of letting the raw timeout exception
  propagate.
- `proc.returncode` is the process's exit code — by convention, `0` means
  success and anything else means failure. If `ffmpeg` failed, its
  `stderr` (error messages it printed) is decoded from bytes to a readable
  string and folded into a `RuntimeError` so callers get a useful message.

```python
    peaks = extract_peaks_from_pcm(stdout, PEAKS_NUM_BUCKETS)
    if resolved_duration_ms == 0:
        total_samples = len(stdout) // BYTES_PER_SAMPLE
        resolved_duration_ms = int((total_samples * 1000) / SAMPLE_RATE)

    return resolved_duration_ms, peaks
```

Last fallback: if mutagen couldn't determine duration earlier, it's now
computed exactly from how many samples `ffmpeg` actually produced, divided
by the sample rate (8,000 samples = 1 second), giving milliseconds. The
function returns a **tuple** `(duration_ms, peaks)` — both pieces of
information a caller needs about this track.

## 6.3 `hasher.py` — deciding a cache file's name

### 6.3.1 What is "hashing," generally?

A **hash function** takes some input data (of any size — a short string, a
whole file, anything) and produces a fixed-size output (often an integer or
a short string of hex digits) called a **hash** or **digest**. Two
important properties make hash functions useful:

1. The *same* input always produces the *same* output, every time, on any
   machine. Feed it `"hello"` today, feed it `"hello"` next year — same
   hash.
2. Different inputs are *extremely* likely to produce different outputs
   (this is called **low collision probability** for a well-designed hash
   function) — though for most hash functions, including this project's, two
   different inputs landing on the same output is not mathematically
   impossible, just astronomically unlikely in practice.

Python's standard library has a dedicated module for this,
`hashlib`, with functions like `hashlib.sha256(data).hexdigest()` for
"cryptographic" hashing (designed to be hard to reverse or fake — used for
things like password storage or verifying a download wasn't tampered with).
This project, however, **does not use `hashlib`** — it implements its own,
much simpler, much faster hash algorithm by hand, because it isn't
protecting against malicious tampering; it just needs a short, deterministic,
collision-resistant-enough **cache key** derived from a file path. That
algorithm is called **FNV-1a**.

### 6.3.2 Why hash a path at all?

Think about what this subsystem needs: given a track at, say,
`Music/Soulection/Show 600.mp3`, it needs to decide on a filename for that
track's cached peaks data (e.g. something like `a1b2c3d4e5f60708.peaks`),
such that:

- The *same* track path always maps to the *same* cache filename (so a
  second run of the tool can find the cache it made last time and skip
  redoing the work — this is the **dedup / cache-matching** use case named
  in the module's own docstring).
- The filename doesn't contain slashes, spaces, or other characters that
  would be awkward or unsafe as a filename, and it doesn't blow up to the
  full length of a deeply-nested path.
- Many different track paths spread out across many different short
  filenames in one flat cache directory, rather than everything colliding.

A hash function is the perfect tool for exactly this: compress an
arbitrary-length, messy path string down into a short, filename-safe,
deterministic identifier.

### 6.3.3 Path normalization first

```python
"""Path normalization and 64-bit FNV-1a hashing for sidecar cache matching."""

FNV1A_64_OFFSET: int = 0xCBF29CE484222325
FNV1A_64_PRIME: int = 0x100000001B3
MASK_64: int = 0xFFFFFFFFFFFFFFFF


def normalize_path(path: str) -> str:
    cleaned = path.strip().replace("\\", "/")
    cleaned = cleaned.lstrip("/")
    return cleaned.lower()
```

Before hashing, paths are normalized so that trivial differences in how a
path is *written* don't change its hash. `path.strip()` removes leading/
trailing whitespace; `.replace("\\", "/")` turns Windows-style backslashes
into forward slashes (so `Music\Artist\Song.mp3` and `Music/Artist/Song.mp3`
normalize identically); `.lstrip("/")` removes any leading slash(es); and
`.lower()` makes it case-insensitive. The test
`test_hash_track_path_normalization_consistency` demonstrates exactly this:
`"Music/Artist/Song.mp3"` and `r"  /Music\Artist\Song.mp3  "` must hash to
the *same* value, because they refer to the same track and should map to
the same cache file.

Numbers like `0xCBF29CE484222325` are **hex literals** — Python lets you
write integers in hexadecimal with a `0x` prefix. These three particular
numbers are not arbitrary: they're the standard constants that define the
FNV-1a algorithm (a fixed starting value, a fixed "prime" multiplier, and a
bitmask that keeps the result constrained to 64 bits).

### 6.3.4 The hash function itself

```python
def fnv1a_64(data: bytes) -> int:
    val = FNV1A_64_OFFSET
    for byte in data:
        val ^= byte
        val = (val * FNV1A_64_PRIME) & MASK_64
    return val
```

This loops over every single **byte** in `data` (iterating over a `bytes`
object in Python gives you back plain integers, one per byte, 0–255). For
each byte:

- `val ^= byte` — XORs ("exclusive or," a bitwise operator) the current
  running hash with this byte, scrambling bits.
- `val = (val * FNV1A_64_PRIME) & MASK_64` — multiplies by the fixed prime
  constant, then applies `& MASK_64` (bitwise AND with
  `0xFFFFFFFFFFFFFFFF`, i.e. 64 one-bits) to **keep the result wrapped
  within 64 bits** — this is Python's stand-in for the integer overflow
  that would happen automatically in a fixed-width language like C; Python
  integers can grow arbitrarily large, so without this mask the number
  would just keep growing forever instead of behaving like a genuine
  64-bit hash.

By the time the loop finishes, `val` encodes information about *every*
byte of the input, in order — change one byte anywhere in the path, and the
final `val` comes out completely different. The test
`test_fnv1a_64_vectors` checks this implementation against known, published
reference values for FNV-1a (`fnv1a_64(b"") == 0xCBF29CE484222325`, etc.) —
a good way to confirm this hand-written algorithm exactly matches the
standard specification, not just "some function that returns different
numbers for different inputs."

### 6.3.5 Turning the hash into a filename

```python
def hash_track_path(path: str) -> str:
    normalized = normalize_path(path)
    h = fnv1a_64(normalized.encode("utf-8"))
    return f"{h:016x}"


def peaks_filename_for_path(path: str) -> str:
    return f"{hash_track_path(path)}.peaks"
```

`normalized.encode("utf-8")` converts the normalized *string* into *bytes*
(hash functions, including this one, operate on raw bytes, not on Python's
text-string type — `encode` is the standard way to make that conversion,
using UTF-8, the near-universal text encoding).

`f"{h:016x}"` is an f-string with a **format spec** you haven't seen before:
everything after the `:` controls *how* the value is rendered. `x` means
"format this integer as lowercase hexadecimal," and `016` means "pad the
result with leading zeroes to at least 16 characters wide." A 64-bit
number in hex is always at most 16 hex digits (since each hex digit covers
4 bits, and 4 × 16 = 64), so this guarantees a fixed-width, 16-character
hex string every time — which is exactly what
`test_hash_track_path_format` checks (`len(h) == 16`). `peaks_filename_for_path`
then just appends the `.peaks` extension this project uses for its cache
files.

## 6.4 `writer.py` — packing peaks into 300 bytes on disk

### 6.4.1 The file format

```python
"""300-byte binary writer and format validator for waveform peaks."""

from collections.abc import Sequence
from pathlib import Path
import struct
from typing import cast

PEAKS_MAGIC: bytes = b"PEAK"
PEAKS_VERSION: int = 1
PEAKS_NUM_BUCKETS: int = 288
PEAKS_HEADER_SIZE: int = 12
PEAKS_FILE_SIZE: int = PEAKS_HEADER_SIZE + PEAKS_NUM_BUCKETS
HEADER_STRUCT: struct.Struct = struct.Struct("<4sHHI")
```

Now you can see the concrete numbers: every `.peaks` file holds exactly
**288 buckets** (`PEAKS_NUM_BUCKETS`), each one byte (0–255), preceded by a
**12-byte header**, for a fixed total of **300 bytes per file**
(`PEAKS_HEADER_SIZE + PEAKS_NUM_BUCKETS`). `b"PEAK"` is a 4-byte
**magic number** — a recognizable fixed byte sequence at the very start of
the file whose only job is to let code (or you, inspecting the file by hand)
quickly confirm "yes, this really is a peaks file, not something else" and
immediately reject garbage.

`struct.Struct("<4sHHI")` was introduced conceptually in Chapter 0, but
here's a precise reading of this particular format string:
- `<` — little-endian byte order.
- `4s` — a 4-byte raw byte string (the magic number).
- `H` — an unsigned 16-bit integer (the format version).
- `H` — another unsigned 16-bit integer (the bucket count, stored
  redundantly in the file itself, so a reader doesn't have to assume 288
  forever).
- `I` — an unsigned 32-bit integer (the track duration in milliseconds).

Pre-building a `struct.Struct` object once (rather than calling the
module-level `struct.pack`/`struct.unpack` functions with a format string
every time) is a minor performance optimization — the format string only
needs to be parsed once, not on every call.

### 6.4.2 `serialize_peaks` — building the bytes

```python
def serialize_peaks(duration_ms: int, peaks: Sequence[int] | bytes) -> bytes:
    if len(peaks) != PEAKS_NUM_BUCKETS:
        raise ValueError(f"Expected {PEAKS_NUM_BUCKETS} peak buckets, got {len(peaks)}")
    header = HEADER_STRUCT.pack(
        PEAKS_MAGIC,
        PEAKS_VERSION,
        PEAKS_NUM_BUCKETS,
        int(duration_ms) & 0xFFFFFFFF,
    )
    payload = bytes(min(255, max(0, int(p))) for p in peaks)
    return header + payload
```

`Sequence[int] | bytes` is a type hint meaning "either an ordered
collection of integers (a `list[int]` or `tuple[int, ...]`, etc.) or
already-raw `bytes`" — `Sequence` is a general abstract type from
`collections.abc` covering anything list-like that supports indexing and
`len()`. This function first **validates** the input (exactly 288 values,
or it refuses with a clear `ValueError` — you can see every one of its
failure modes exercised directly in `test_serialize_invalid_bucket_count`).

`HEADER_STRUCT.pack(...)` packs the four header fields into 12 raw bytes,
in the exact order and widths described above.  `int(duration_ms) &
0xFFFFFFFF` clamps the duration into the range a 32-bit unsigned integer
can represent, just in case.

`payload = bytes(min(255, max(0, int(p))) for p in peaks)` is worth
slowing down on. `bytes(some_generator_of_ints)` is a **constructor
call**: the `bytes` type in Python can build itself directly from any
iterable of small integers (each must be 0–255), producing one byte per
value — exactly the "list of 288 bucket values" becoming "288 raw bytes"
conversion this function needs. Inside the generator,
`min(255, max(0, int(p)))` **clamps** each value: `max(0, int(p))` forces
anything below 0 up to 0, then `min(255, ...)` forces anything above 255
down to 255. This protects against callers accidentally passing
out-of-range numbers — `test_serialize_clamps_peak_values` confirms values
like `-10` become `0` and `300` becomes `255` in the final file.

Finally, `header + payload` — this is `bytes` **concatenation** (the `+`
operator works on `bytes` just like it works on strings or lists),
producing the complete 300-byte blob: 12 header bytes followed by 288
payload bytes.

### 6.4.3 `deserialize_peaks` — reading it back and validating it

```python
def deserialize_peaks(data: bytes) -> tuple[int, list[int]]:
    if len(data) != PEAKS_FILE_SIZE:
        raise ValueError(
            f"Invalid peaks data length: expected {PEAKS_FILE_SIZE} bytes, got {len(data)}"
        )
    unpacked = cast(
        tuple[bytes, int, int, int],
        HEADER_STRUCT.unpack(data[:PEAKS_HEADER_SIZE]),
    )
    magic, version, num_buckets, duration_ms = unpacked
    if magic != PEAKS_MAGIC:
        raise ValueError(f"Invalid magic: expected {PEAKS_MAGIC!r}, got {magic!r}")
    if version != PEAKS_VERSION:
        raise ValueError(
            f"Unsupported version: expected {PEAKS_VERSION}, got {version}"
        )
    if num_buckets != PEAKS_NUM_BUCKETS:
        raise ValueError(
            f"Invalid bucket count: expected {PEAKS_NUM_BUCKETS}, got {num_buckets}"
        )
    return duration_ms, list(data[PEAKS_HEADER_SIZE:])
```

This mirrors `serialize_peaks` in reverse, with explicit validation at
every step — a good pattern to notice generally: **anything that reads a
file format you wrote should verify the file is actually what it claims to
be**, rather than trusting blindly. Each check (overall length, magic
bytes, version number, bucket count) has its own dedicated test in
`test_peaks_writer.py` (`test_deserialize_invalid_length`,
`test_deserialize_invalid_magic`, `test_deserialize_invalid_version`,
`test_deserialize_invalid_bucket_count_in_header`), each constructing a
deliberately broken file and confirming the right error message comes back.

`cast(tuple[bytes, int, int, int], HEADER_STRUCT.unpack(...))` — `cast` is
from the `typing` module and does **nothing at runtime**; it's purely a hint
to static type checkers (like pyright, which this project uses — note the
`# pyright: ignore[...]` comment you saw in `extractor.py` earlier) telling
them "trust me, I know this unpack call returns exactly these four types,"
since `struct.unpack`'s return type is otherwise too generic for the checker
to know precisely.

`data[PEAKS_HEADER_SIZE:]` is a **slice** — everything from byte index 12
to the end — and `list(...)` converts that `bytes` slice into a plain
`list[int]`, since callers of this function (like the tests, and
`manager.py`) want to work with ordinary Python integers, not a raw bytes
object.

### 6.4.4 `write_peaks_file` — atomic writing to disk

```python
def write_peaks_file(
    file_path: str | Path,
    duration_ms: int,
    peaks: Sequence[int] | bytes,
) -> None:
    path = Path(file_path) if isinstance(file_path, str) else file_path
    path.parent.mkdir(parents=True, exist_ok=True)
    data = serialize_peaks(duration_ms=duration_ms, peaks=peaks)
    temp_path = path.with_suffix(".tmp")
    try:
        with temp_path.open("wb") as f:
            _ = f.write(data)
        _ = temp_path.replace(path)
    except Exception:
        temp_path.unlink(missing_ok=True)
        raise
```

`path.parent.mkdir(parents=True, exist_ok=True)` creates any missing parent
directories (`parents=True` means "create intermediate directories too, not
just the immediate one"; `exist_ok=True` means "don't error if it already
exists").

The real point of interest is **why this writes to a temporary file first**
instead of writing directly to the final filename. `temp_path.open("wb")`
opens a file for **binary writing** (`"w"` = write, `"b"` = binary mode —
without `"b"`, Python would try to treat the data as text and could corrupt
raw bytes). It writes the complete serialized data there, then calls
`temp_path.replace(path)`, which **atomically** renames the temp file onto
the final target filename. "Atomic" means: from the perspective of any
other program reading `path` at the same time, the file either doesn't
exist yet, or it exists *complete and correct* — there's no possible moment
where a reader could see a half-written, corrupt `.peaks` file, which could
otherwise happen if you wrote directly into the final file and the process
crashed or was interrupted partway through.

If *anything* goes wrong during this process (`except Exception`), the
leftover `.tmp` file is cleaned up (`temp_path.unlink(missing_ok=True)` —
delete it, and don't complain if it's already gone) before the original
exception is **re-raised** (the bare `raise` with nothing after it inside an
`except` block means "re-raise whatever exception we just caught,"
preserving the original error instead of hiding it).
`test_write_peaks_file_cleanup_on_exception` verifies exactly this: it
simulates a failure during the final rename step and confirms the leftover
temp file does *not* survive.

## 6.5 `manager.py` — the coordinator

### 6.5.1 Why have a "manager" at all?

Each of the three modules above does one focused job and knows nothing
about the others — `extractor.py` doesn't know what a cache filename looks
like; `hasher.py` doesn't know anything about audio or binary formats;
`writer.py` doesn't know where files come from. `manager.py` is the piece
that **knows about all three** and calls them in the right order, for every
track in a whole music library. This is a common design pattern worth
naming explicitly: a small class or set of functions whose entire
responsibility is *orchestration* — deciding *when* and *in what order* to
call other, simpler pieces — rather than doing any of the actual work
itself. You'll sometimes hear this called a "coordinator" or "orchestrator."

```python
"""Batch waveform peaks manager."""

from collections.abc import Callable
import concurrent.futures
import logging
import os
from pathlib import Path

from dap_db_manager.peaks.extractor import extract_peaks
from dap_db_manager.peaks.hasher import peaks_filename_for_path
from dap_db_manager.peaks.writer import write_peaks_file

AUDIO_EXTENSIONS: set[str] = {
    ".mp3",
    ".flac",
    ".m4a",
    ".aac",
    ".alac",
    ".wav",
    ".ogg",
    ".opus",
}
```

Notice the imports: exactly one function from each of the other three
files. `AUDIO_EXTENSIONS` is a `set[str]` (a Python `set`, met in
Chapter 0 — unordered, unique values, fast membership checks with `in`)
listing every file extension this project recognizes as "this is probably
an audio file worth generating peaks for."

### 6.5.2 `resolve_peaks_dir` — where do cache files live?

```python
def resolve_peaks_dir(target_dir: Path) -> Path:
    path = Path(target_dir)
    if path.name == ".rockbox":
        return path / "soulectionpod" / "peaks"
    if path.parent.name == ".rockbox":
        return path.parent / "soulectionpod" / "peaks"
    if (path / ".rockbox").is_dir():
        return path / ".rockbox" / "soulectionpod" / "peaks"
    return path / ".rockbox" / "soulectionpod" / "peaks"
```

This is plain path arithmetic using `pathlib.Path` (met in Chapter 0): given
some directory the user pointed the tool at, figure out where the
`.peaks` cache files should actually live, relative to the device's
`.rockbox` folder (recall from Chapter 1 that `.rockbox` is where Rockbox
keeps its own database files). It handles a few different cases of "what
kind of directory did the caller pass in" — the device's `.rockbox` folder
itself, something *inside* `.rockbox` (like a `database` subfolder), a DAP
root that already *contains* a `.rockbox` folder, or a brand-new directory
that doesn't have one yet (the final fallback). `path / "soulectionpod" /
"peaks"` is `pathlib`'s overloaded `/` operator for joining path segments —
cleaner than manually concatenating strings with slashes.

### 6.5.3 `process_single_track` — the full pipeline, for one file

This is where all three sibling modules meet:

```python
def process_single_track(
    audio_path: Path,
    rel_path: str,
    output_dir: Path,
    force: bool = False,
) -> str:
    audio_file = Path(audio_path)
    out_dir = Path(output_dir)
    dest = out_dir / peaks_filename_for_path(rel_path)

    if not force and dest.exists():
        try:
            if dest.stat().st_mtime >= audio_file.stat().st_mtime:
                return "skipped"
        except OSError:
            pass

    try:
        duration_ms, peaks = extract_peaks(audio_file)
        write_peaks_file(dest, duration_ms, peaks)
        return "generated"
    except Exception as e:
        logging.error("Failed to generate peaks for %s: %s", audio_file, e)
        return "error"
```

Read this top to bottom as the whole story:

1. `peaks_filename_for_path(rel_path)` — call into `hasher.py` to decide
   the cache filename for this track's relative path.
2. **Caching check**: `dest.stat().st_mtime` is the cache file's
   **modification time** (as a Unix timestamp — seconds since a fixed
   reference point); comparing it against the *source audio file's*
   modification time answers "has the cache already been generated *after*
   the audio file was last changed?" If yes, and the caller didn't pass
   `force=True`, this track is skipped entirely — no decoding, no `ffmpeg`
   subprocess, nothing. This is exactly why peaks generation can afford to
   be slow per-file: **most runs, most files are already cached and get
   skipped in microseconds.** `except OSError: pass` quietly ignores
   filesystem errors during this check (e.g. a race where the file
   disappears mid-check) and just falls through to regenerating.
3. **Extraction + writing**: if not skipped, call into `extractor.py`
   (`extract_peaks`) to get `(duration_ms, peaks)`, then immediately call
   into `writer.py` (`write_peaks_file`) to persist them.
4. The function returns one of three plain strings — `"skipped"`,
   `"generated"`, or `"error"` — rather than raising exceptions for
   ordinary per-track failures. This matters because of *how* this function
   gets called next: across potentially thousands of tracks, in parallel,
   where you don't want one corrupt audio file to crash the entire batch.
   `logging.error(...)` records the failure (with the real exception
   message `e`) so it's visible afterward, while the surrounding
   `generate_peaks_for_library` keeps going.

### 6.5.4 `generate_peaks_for_library` — fanning out across a whole library, in parallel

```python
def generate_peaks_for_library(
    music_dir: Path,
    output_dir: Path,
    dap_root: Path | None = None,
    jobs: int | None = None,
    force: bool = False,
    progress_callback: Callable[[int, int], None] | None = None,
) -> tuple[int, int, int]:
```

`progress_callback: Callable[[int, int], None] | None` is a type hint for
"an optional function that takes two `int` arguments and returns nothing" —
this lets a CLI or GUI caller plug in their own "update a progress bar"
logic without `manager.py` needing to know anything about progress bars
itself (another small instance of the orchestrator *not* doing work that
belongs elsewhere).

```python
    music_path = Path(music_dir)
    out_path = Path(output_dir)
    out_path.mkdir(parents=True, exist_ok=True)

    tracks: list[tuple[Path, str]] = []
    if music_path.is_dir():
        for p in music_path.rglob("*"):
            if p.is_file() and p.suffix.lower() in AUDIO_EXTENSIONS:
                try:
                    if dap_root is not None and p.is_relative_to(dap_root):
                        rel = str(p.relative_to(dap_root))
                    else:
                        rel = str(p.relative_to(music_path))
                except ValueError:
                    rel = p.name
```

`music_path.rglob("*")` **recursively** walks every file and folder under
`music_dir` (`rglob` = "recursive glob" — met conceptually in Chapter 0's
discussion of paths; the `"*"` pattern matches everything). For every real
file whose extension (lowercased) is in `AUDIO_EXTENSIONS`, it computes a
**relative path** string — relative to `dap_root` if one was given,
otherwise relative to `music_dir` itself — which is exactly the string
`hasher.py`'s `peaks_filename_for_path` will hash. This relative-path
choice matters: it's *why* the same track produces the same cache filename
across different runs (and potentially different machines), as long as its
position relative to the DAP root stays the same.

```python
                if (
                    not rel.lower().startswith("music/")
                    and music_path.name.lower() == "music"
                ):
                    rel = f"music/{rel}"

                tracks.append((p, rel))

    tracks.sort(key=lambda t: t[1])
```

A small normalization: if the music folder itself is literally named
`Music` but the relative path doesn't already start with `music/` (because
it was computed relative to that same folder), prepend `music/` so paths
stay consistent with how tracks are referenced elsewhere in the project
(recall from Chapter 1 that paths inside the Rockbox database are usually
written as `Music/...`). `tracks.sort(key=lambda t: t[1])` sorts the list
of `(path, rel_path)` tuples by the **second** element of each tuple (the
relative path string) — a `lambda` is a small, anonymous, one-expression
function, here just "given tuple `t`, return `t[1]`." Sorting gives
deterministic, reproducible ordering across runs (useful for consistent
logs and progress reporting), even though — as we'll see next — the actual
*work* doesn't happen in this order.

```python
    max_workers = jobs or os.cpu_count() or 4
    generated_count = 0
    skipped_count = 0
    completed = 0

    with concurrent.futures.ProcessPoolExecutor(max_workers=max_workers) as executor:
        futures = [
            executor.submit(process_single_track, audio_file, rel_path, out_path, force)
            for audio_file, rel_path in tracks
        ]
        for future in concurrent.futures.as_completed(futures):
            try:
                res = future.result()
            except Exception as e:
                logging.error("Worker error during peak generation: %s", e)
                res = "error"

            if res == "generated":
                generated_count += 1
            elif res == "skipped":
                skipped_count += 1

            completed += 1
            if progress_callback is not None:
                progress_callback(completed, total_tracks)

    return total_tracks, generated_count, skipped_count
```

This is the payoff for making `process_single_track` a single, self-contained
function that returns a plain string instead of mutating shared state:
`concurrent.futures.ProcessPoolExecutor` runs it across **multiple
operating-system processes** at once — `max_workers = jobs or
os.cpu_count() or 4` picks however many the caller requested, or one per
CPU core, or `4` as a last-resort default if `os.cpu_count()` can't
determine that. Each `executor.submit(...)` call schedules one track's
`process_single_track(...)` to run (possibly on a different CPU core,
possibly at the same time as several others), immediately returning a
`Future` object — a placeholder representing "this result will exist
eventually." `concurrent.futures.as_completed(futures)` then hands back
each `Future` *as it finishes* (not necessarily in submission order — so
your terminal's progress output may jump around for individual tracks, even
though the final counts are correct).

This is directly why decoding every audio file with `ffmpeg` — genuinely
slow, as discussed in 6.1 — is tolerable at library scale: instead of one
track's extraction blocking the next, this project spreads the work across
every available CPU core simultaneously. Combined with the modification-time
caching inside `process_single_track`, a second run over an unchanged
library finishes almost instantly (every track is `"skipped"`), and a first
run over a large library is bounded by core count rather than track count.
